# PC Web Core Promotion Record

## Promoted Artifact

Promote `docs/design/decisions/pc-web-core-surface-decision-v1.md` and `docs/design/mocks/pc-web-core-surfaces-v1.html` as the design-only PC Web authority. Future implementation must consume `docs/design/mapping/pc-web-core-implementation-map-v1.md`.

## Winning Candidate

`pcw-01` is the winning base. It borrows the answer slip from `pcw-02`, the dedicated Space hierarchy from `pcw-03`, and the keyboard/focus discipline from `pcw-04`.

## Baseline Comparison

The winner extends the accepted platform layout decision from prose into contained 1440 x 900 renderings. It improves the baseline by proving Auth, all five interaction silhouettes, resolved review, attached audio, Space hierarchy, Statistics, Mine, and membership interruption inside one PC Web grammar. It does not replace production accessibility or browser evidence; those remain implementation obligations.

## Borrowed Fragments

- `pcw-02`: answer and explanation as an attached exam-material slip.
- `pcw-03`: library / group tree, current box workbench, contained cards, and right inspector on Space.
- `pcw-04`: predictable keyboard focus order, restrained key hints, and discrete reduced-motion equivalents.

## Rejected Fragments

- `pcw-05`: metrics, schedule, and progress as the first read.
- `pcw-06`: equal multi-card or multi-module choices.
- `pcw-07`: movable windows and arbitrary workspace organization.
- `pcw-08`: module catalogue as the default Learning entry.

## Implementation Mapping Expectations

Future Web implementation must map the left route rail, center focal-object workbench, bounded right context rail, five shape-level interaction branches, attached review and audio states, Space tree / box / inspector, quiet Statistics ledger, Mine account object, login gate, and contextual membership interruption. The implementation PR must be separate from this design-only promotion.

## Unimplemented Gaps

- No production Web application, hosting configuration, authentication call, runtime client, purchase flow, or deployment is created here.
- Exact content density must be validated against approved content payloads; this artifact uses anonymous exam-oriented copy only.
- Real browser keyboard, screen-reader, zoom, reduced-motion, light/dark, and responsive evidence remain required.
- Tablet still requires its own rendered proof before tablet-specific implementation.
- Production payment and SMS states remain externally gated.

## Failure Sedimentation

The recurring PC Web failures are recorded in `docs/design/rejected/pc-web-core-surface-failures-v1.md`: dashboard-first, multi-card grid, floating window manager, and module-catalogue-first. Existing product and visual specs already reject these patterns, so no product-truth mutation is needed.

## Design Review Checklist Answers

Q1: Learning proofs use one active library and coral is its sole strong accent. Space keeps that active library while other libraries remain low-weight tree dots. Auth, Statistics, Mine, and membership use neutral chrome rather than inventing a second library accent.

Q2: Focal objects are the login card for Auth, current knowledge card for Learning/review/audio, current box or selected card for Space, daily ledger for Statistics, account object for Mine, and affected current object for membership interruption. The first-read path remains focal object -> operation/state -> rails.

Q3: The rendered proof includes distinct flip, multiple-choice, lock, elimination, and swipe silhouettes. Space uses tree -> current box -> contained cards -> inspector.

Q4: No gradient text, serif dependency, reward chrome, full-width bottom navigation, removed self-assess tokens, or user-visible internal language appears.

Q5: Not a phone proof. Every frame is contained at the 1440 x 900 PC Web reference size with no horizontal overflow.
