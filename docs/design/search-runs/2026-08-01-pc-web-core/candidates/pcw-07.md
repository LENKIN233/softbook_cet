# PC Web Candidate: Floating Windows

## Candidate ID

`pcw-07`

## Provenance

- Tool or model: Codex negative-direction composition.
- Prompt: Place Learning, notes, Space, audio, and progress in movable floating glass windows.
- Source context pack: `../context-pack.md`.
- Artifact: `candidate-proofs/pc-web-candidate-proof.html#pcw-07`.
- Screenshots: `candidate-proofs/pc-web-candidate-proof.html#pcw-07`.

## Product Truth Fit

Fails low-burden guidance and physical Space ownership by asking the learner to manage windows and layout.

## Focal Object

Ambiguous among overlapping windows.

## First-Read Path

Window chrome -> overlapping panels -> current card.

## Interaction Silhouette

Each interaction becomes a resizable panel rather than a stable canonical shape.

## Spatial Model

Spatiality is confused with desktop window placement; card ownership is not expressed.

## State Language

Window focus replaces product state.

## Motion Causality

Dragging windows is arbitrary organization, not a supported learning or Space operation.

## Platform Strategy

Uses PC conventions literally and makes touch-exclusive organization worse rather than adapting meaning.

## Implementation Mapping

Would invent a window manager and state system outside accepted contracts.

## Known Risks

- High operational cost.
- Arbitrary spatial reassignment metaphor.
- Accessibility and focus-order instability.

## Design Review Checklist Answers

Q1: Multiple panels create accent competition.

Q2: No stable focal object.

Q3: Interaction and Space silhouettes fail.

Q4: Glass itself is allowed, but floating-window chrome is structurally wrong.

Q5: Overlap makes containment unreliable.

Q6: Learning is no longer a guided path; rejected.
