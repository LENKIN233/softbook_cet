# PC Web Candidate: Progress Dashboard

## Candidate ID

`pcw-05`

## Provenance

- Tool or model: Codex negative-direction composition.
- Prompt: Use desktop width for progress, schedule, counters, and recent activity around a compact study card.
- Source context pack: `../context-pack.md`.
- Artifact: `candidate-proofs/pc-web-candidate-proof.html#pcw-05`.
- Screenshots: `candidate-proofs/pc-web-candidate-proof.html#pcw-05`.

## Product Truth Fit

Fails because metrics and planning become equal to or stronger than the current card, turning the product into a study-management dashboard.

## Focal Object

Ambiguous between progress chart, schedule, and current card.

## First-Read Path

Metrics -> schedule -> activity -> current card, which is the wrong order.

## Interaction Silhouette

The current-card silhouette is reduced to one dashboard tile.

## Spatial Model

Space becomes a status widget rather than a physical hierarchy.

## State Language

Counters and trends dominate; favorite and sleep lose their spatial semantics.

## Motion Causality

Chart animation has no direct relation to knowledge-object operations.

## Platform Strategy

Uses width to increase information density instead of reducing burden.

## Implementation Mapping

Would create dashboard components outside the accepted product center.

## Known Risks

- Direct product-truth violation.
- Achievement and counter pressure.
- Learning becomes secondary.

## Design Review Checklist Answers

Q1: Fails Law of One through competing status colors.

Q2: No single focal object.

Q3: Fails the current-card silhouette.

Q4: Risks dashboard and achievement chrome.

Q5: Contained but product-wrong.

Q6: Statistics displaces Learning; rejected.
